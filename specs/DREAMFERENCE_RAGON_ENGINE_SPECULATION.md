# ragon-engine: Speculative decoding

Part of the ragon-engine specification; the index is [README.md](./README.md). Section numbers are those of the single-file `SPEC.md` this was split from (Nov 1, 2026 · revised the same day against Ragon's measured workload), so a citation of the form `§n` or `S§n` in the reports and the code still names the same text.

## 10. Speculative decoding: more tokens per pass

Speculation is the only multiplier on a bandwidth-bound machine, so this section is where the targets are won or lost. The design keeps DFlash2 as the drafter, because a block drafter fits this bus, runs it more cheaply, and adds a second draft source that fits what agents write.

Why DFlash2 and not EAGLE-3. An autoregressive drafter makes one pass per draft token; on a 273 GB/s bus even a 1 GB drafter costs 4 ms per token, 28 ms for seven, a third of a target pass. DFlash2 drafts the whole block in one pass by denoising mask tokens conditioned on the target's hidden states, so drafting costs one small pass whatever the block size. The community measures its acceptance at ~6.0 tokens per step on math and ~3.3 on long prose, and production measures 4.87 on Ragon's agent workload with 16 draft tokens.

Changes to how the drafter runs (production already uses the NVFP4 build, so its weights are not a lever):

- *(Done 2026-11-03, [BACKLOG §19](./DREAMFERENCE_RAGON_ENGINE_BACKLOG.md) item 33.)* The BF16 matrices the NVFP4 build left, the fc over the target's features and the conv kernel projections, read as NVFP4 copies rounded at load, on by default (`--draft-bf16` turns them off). Lossy in the drafter only: the verify stays exact, so the output is unchanged and only acceptance can move.

- *(Superseded 2026-11-02 by [BACKLOG §19.19](./DREAMFERENCE_RAGON_ENGINE_BACKLOG.md), the context-aware sparse head: a static list cost −5.7% acceptance on average and −33% on multilingual prompts where it was measured.)* Give it a reduced-vocabulary head over the 32k most frequent tokens, 0.16 GB in FP8, instead of a second pass over the 0.72 GB target head. Candidate selection runs over that subset; its top-K codebooks stay in BF16 as in the W8 recipe. M3 measures the acceptance cost and falls back to a 64k head if it exceeds 0.2 accepted tokens.
- Keep its features resident: the target hidden states it conditions on are written by the target's own kernels at layers 5, 19, 33, 47 and 61, so the drafter never recomputes anything over the context.
- Capture it in the same CUDA graph as the verify, so a step is one graph launch.

**The hybrid tree: DFlash2 plus context lookup.** Agents copy: 46% of the visible tokens Ragon's agent writes continue a match in its own context (file contents into patches, paths and names into commands, earlier tool calls into new ones). A CPU matcher over the session's tokens (context and output so far) looks up the last 3 tokens and proposes the continuation of their most recent occurrence, up to 32 tokens. Its proposal is verified as a second branch beside the DFlash2 draft in the same pass (16 + up to 32 rows), and the accept kernel keeps whichever branch accepts more. On the recorded sessions, a simulation that draws DFlash2's acceptance from production's measured mean gives 4.66 tokens per step for DFlash2 alone and 6.2 with the lookup branch (5.9 with 16 lookup tokens, 6.3 with 64). That simulation treats the two sources as independent, while in reality both succeed on the same copyable spans, so 6.2 is an upper bound; the target is 5.8 and M2 measures the real number on the replay. The matcher costs microseconds and runs during the previous step.

**Verification shape.** Row buckets of 16, 32, 48 and 64 are compiled. The default for a single sequence is DFlash2's 16 draft tokens, arranged as a tree of block 8 with the top-K selector's alternatives at the first uncertain positions (whether production already does this is M0's question) plus the lookup branch when the matcher has a proposal; for a batch, each sequence gets 16 rows and the lookup branch only when it has a match of 8 or more tokens. M2 measures accepted tokens per millisecond for each shape on the replay and picks per request class. As built (2026-11-03, on by default; [BACKLOG §19](./DREAMFERENCE_RAGON_ENGINE_BACKLOG.md) item 26): a one-stream step of a full block verifies the chain's first 8 drafts plus the 7 best other candidates by path probability (temperature 1.5) as a tree of 16 rows in one pass (`--tree`, `RAGON_TREE`); batches, lookup chains and `logprobs` requests verify the chain.

**The drafter-off guard** (built 2026-11-04, [BACKLOG §19](./DREAMFERENCE_RAGON_ENGINE_BACKLOG.md) item 10; `core/draft_guard.hpp`). A speculative step costs 1.11-1.12 plain steps (95.3 against 84.9 ms at 4K, 100.8 against 91.0 at 32K, measured 2026-11-04), at most ~1.24 against a graph-captured one-row pass, so the drafter loses only below ~1.12-1.24 tokens per step (accepted drafts + 1); agent work runs at 4-7. Each session keeps an EMA (α = 1/16) of its speculative steps' tokens per step. After 16 steps of warm-up, a mean below `--draft-off-below` (1.5; 0 turns the guard off) switches the session's drafter off: its steps become plain one-row decodes (`Engine::step`, the path of a request without speculation), and after every 16 of them one speculative step probes the drafter and feeds the mean; at 1.5 + 0.25 the drafter is on again. The margin over break-even is deliberate: off when the drafter would win costs up to ~45% of the throughput at 2 tokens per step, on when it loses at most ~11%. Three properties make a switch free and exact. *The drafter's context*: `Engine::step` writes the row's target features (every forward pass copies the feature layers into the capture buffer) into the drafter's context ring at its position, as a commit does for its accepted rows, so the ring holds every position whichever path processed it and the first step after a switch drafts from the context it would have had; `ragon-run --spec-check` compares the ring after a guarded run with a plain replay's, bit for bit. *The state*: the plain pass advances the DeltaNet and conv state itself, after joining any overlapped commit. *The tokens*: the rows path is row-invariant, so greedy output is token for token plain decoding's whether the guard trips or not; sampled output keeps its distribution but not its tokens (`sample()` draws once from the full chain, a speculative step draws its path and the rejection rule), which is already how a speculative request relates to a plain one; so that every output token stays as it was, the guard applies to greedy requests only by default, and `RAGON_DRAFT_OFF_SAMPLED=1` extends it to sampled ones (the owner's call: the same distribution, other tokens). In a batch a session whose next step is plain takes that step alone (`can_batch` is false), as a plain request does; a probe may join. Counted in `/spec_stats` (`drafter_off_steps`, `drafter_switches`) and `/metrics`.

**An agent-tuned drafter (stretch).** DFlash2 was trained on generic data; Ragon's agent writes tool calls, patches and short status text. The drafter is small (5 layers, ~1.9B parameters) and its training signal is the target's own output, which Ragon already produces every night. A fine-tune on the user's own recorded sessions is feasible on the Spark itself: about 11 GFLOP per training token for the drafter, so 50M tokens are roughly 570 PFLOP, a few hours, plus a few hours of target forward passes to produce the hidden features. Nothing leaves the machine, and the result is specific to how this user's agent works. The fine-tune competes with Night Shift for the same memory and hours, so it runs under the same admission as other night work, on nights with time to spare. The target is acceptance 8 on the replay; it is scheduled after M4 and nothing before it depends on it. A block-16 retrain is the same work with a different block size.

Only the attention core depends on context: going from 25.7K to 2K saves 5.1 ms, all of it there. The megakernel stamps (`RAGON_MK_TIMES=1`) split an FFN layer's 672 us as follows:

- gate and up: 417 us at 240 GB/s;
- between them and down: 25 us of done flags, SiLU, row maxima and the grid barrier;
- down: 208 us at 241 GB/s;
- the tail norm: 20 us.

That leaves the bus idle for 45 us a layer, 2.8 ms per step. A DeltaNet layer takes 532 us against 481 us for its bytes at 240 GB/s. On the chain's blocks the conv (40 us) and the recurrence (93 us) take about as long as in_z on the streaming blocks.

The levers that keep the greedy output bitwise identical, with what each can save per step at 25.7K:

1. *Query rows per attention block* (one kernel round, measured). Instead of 96, a block takes 48, 32 or 16 query rows. A row's keys, ranges and tile order do not depend on its block, and the output was identical in every arm. The change saves 1.0 ms at 2K (4 to 8 live blocks) but costs 0.7 ms at 25.7K, and 8.4 ms at 16 rows. The probable causes, not measured apart: 56 or more live blocks need a second wave at one 67.6 KB block per SM, and each extra block reads its range's keys and values again. Half the stages (48 rows with a single 33.8 KB stage, the same arithmetic) was not tried. It was not kept. Changing the key range's size (`RAGON_ATTN_CHUNK`) is not exact, since it changes the combine, and 2,048 keys is also slower at 25.7K (verify +1.9 ms, 52 live blocks).
2. *Ship the drafter's sparse head* ([BACKLOG §19.19](./DREAMFERENCE_RAGON_ENGINE_BACKLOG.md)). It is on by default but reads `<drafter>/sparse-head/model.safetensors`, written by `bench/sparse_head/build.py`. Where that file is missing, the drafter runs the full 0.72 GB head (3.0 ms). Its saving, measured in §19.19's rework, not by this job: 1.0 to 1.8 ms per step. It needs no kernel work, only an asset shipped with the drafter. Greedy output is unchanged by construction, because only the proposals change; acceptance can move, which is §19.19's gate.
3. *FFN layer bubbles.* The ceiling is the 2.8 ms above; about 1 to 1.5 ms is realistic, by keeping weights streaming across the two grid barriers of a layer. This takes more than one round. For comparison, the persistent FFN saves only 0.3 ms over the stream GEMMs (`RAGON_MK_FFN=0`: 98.8 ms).
4. *Commit and DeltaNet critical path.* Fusing the commit's replay into the next verify could save 1 to 2 ms; without the commit overlap (`RAGON_COMMIT_OVERLAP=0`) the host-timed commit goes from 0.8 to 2.6 ms. Shortening the DeltaNet chain could save about 1 ms. Each takes several rounds.

The verdict: 90 ms at 25.7K is not reachable with exact levers alone. At the 240 GB/s the persistent kernels sustain, the step's bytes alone take about 88 ms. Reaching 90 would mean recovering about 8 of the roughly 10 ms of overhead above that. The exact levers above add up to 4-6 ms at best, which gives about 92-94 ms. The rest needs the low-bit levers of [LOWBIT](./DREAMFERENCE_RAGON_ENGINE_LOWBIT.md): by bytes, NVFP4 attention and DeltaNet projections save about 12.5 ms and an FP8 KV cache about 3.2 ms at 25.7K.

**Exactness.** Under greedy decoding a draft token is accepted only if it equals the target's argmax, so the output is identical to plain decoding; under sampling the accept kernel uses the standard rejection rule with the drafter's probabilities (the lookup branch is a deterministic proposal, probability 1), which preserves the target distribution. The Qwen sampling chain (temperature, top-k 20, top-p, min-p, presence penalty 1.5 in instruct mode) is applied to the target logits before acceptance, so penalties are honoured exactly. The MTP module ships with the model and is kept as a fallback drafter; it is autoregressive and about one layer in size, so it drafts 3–4 tokens at modest cost and is only used if no DFlash2 drafter exists for a checkpoint.
